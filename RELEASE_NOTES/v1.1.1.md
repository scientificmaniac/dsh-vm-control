# dsh-vm-control v1.1.1 · 修复电源工具的挂死

一次 `vm_power start`（`gui: true`）在虚拟机**已经成功启动**的情况下持续 4 分 12 秒没有返回，最后只能手动中断，宿主因此记下 `TOOL_OUTCOME_UNKNOWN`。本版修复这个问题，并把电源动作的等待语义改成可预期的。

## 修复 / Fixed

### 电源工具为什么可能永不返回

根因不是超时太短，而是 `runProcess` 只监听子进程的 `close` 事件。

`close` 要等**所有** stdio 管道都关闭才触发。`vmrun start <vmx> gui` 会拉起 `vmware.exe` 图形窗口，而那个进程**继承了本进程的 stdout/stderr 管道**。超时后我们 kill 掉 `vmrun.exe`，但窗口仍在运行、仍持有管道，于是 `close` 永远不来，promise 永不落定：

- 调用方看到的是「工具无响应」，而不是一次「已超时」的结果；
- 后续的状态确认逻辑根本没机会执行；
- 中断后宿主无法判断副作用是否已落地，只能记 `TOOL_OUTCOME_UNKNOWN`。

现在 `exit`（在直接子进程退出时触发）之后会补一个 250ms 的兜底落定。正常路径仍然由 `close` 抢先，保证 stdout 完整；管道被孙进程占住时由兜底收尾。**孙进程是虚拟机本身，不会为了收管道去杀它。**

### 等待预算改为共用总额

此前 vmrun 自身的超时与随后的状态确认各算各的（启动 120 秒 + 确认 45 秒），一次卡住的调用最坏能挂到 165 秒。现在 `timeoutMs` 是整次调用的总额，确认阶段只拿剩余部分；vmrun 把预算花光时仍保留 5 秒最短窗口——`vmrun list` 往往在命令返回后几百毫秒内才反映新状态，一次都不查就报「未确认」是假阴性。

### GUI 启动单独设 60 秒默认超时

图形窗口出现并不代表虚拟机就绪，继续等只会把「已启动」拖成「超时」。

### 超时不再被判成失败

这是同一个问题的另一半。命令被超时终止只说明「没在时限内返回」，而启动请求早已交给 VMware——虚拟机很可能已经起来了。旧代码直接判失败，等于谎报一次成功的启动，调用方还可能据此重试。

现在超时 / 取消会继续走状态确认，由**实际状态**决定结论，并在结果里标出 `indeterminate`。只有 vmrun 明确报错（vmx 不存在等）才判失败。

实测（真实 vmrun，2 秒超时启动 gui，命令必定被杀）：

```
CentOS 7：已停止 → 运行中（start）
vmrun 没在时限内返回（命令被中止），但随后查到的状态就是 start 之后该有的样子：
结论来自实际状态，不是来自 vmrun 的退出码。
```

### 「已挂起」状态此前从未被正确识别

代码查找挂起镜像是拼 `<name>.vmss`，而 VMware 实际写的是 `<name>-<hash>.vmss`——实测文件名为 `CentOS 7-b846c30e.vmss`，那个哈希由 VMware 生成，不在 vmx 里。

后果是所有挂起状态都被显示成「已停止」：`suspended` 这个状态词在真实机器上根本没出现过，挂起的虚拟机既看不出被挂起，也拿不到「`start` 可以唤醒它」这条提示。

现在按目录前缀扫描 `<name>-*.vmss`，并保留精确匹配；前缀带 `-`，以免把 `CentOS 7 最小系统` 误认成 `CentOS 7` 的挂起镜像（这两台机器上正好都有）。

## 变更 / Changed

- **「未确认」的措辞改为「已发出、未确认」**，并列出已确认的事实，明确区分「没看到结果」与「操作失败」，指引调用方先读状态而不是重发。`vm.powerTimeout` 由 `vm.powerIssuedUnconfirmed` + `vm.powerFacts` 取代。
- 工具描述写明：优先 `gui=false`；`timeoutMs` 是整次调用的总额；未确认时不要重发。
- 无头启动成功时补一行提示，说明它比 GUI 快且不占桌面会话。

## 实测数据 / Measured

本版在一台 CentOS 7.9 桌面版（8 vCPU / 4096 MB，VMware Workstation 17.6，vmrun 1.17.0）上冷启动实测，走的是插件自己的 `inventory.power()` 路径：

| 阶段 | nogui | gui |
| --- | --- | --- |
| `vmrun start` 自身耗时 | 6.1 s | 2.9 s |
| `power()` 完整返回（含状态确认） | 6.71 s · confirmed | 3.48 s · confirmed |

同时观察到一件与工具无关、但值得知道的事：**`vmrun start` 返回 ≠ 虚拟机可用**。上表那次冷启动里，`vmrun` 在 3.1 秒就返回了，而 VMware Tools 直到约 95–155 秒后才报告客户机 IP。要连 SSH 的话，应当轮询 `getGuestIPAddress` 或直接探测 22 端口，而不是拿 `vmrun` 的返回时刻当成就绪时刻。

## 安装 / Install

```bash
dsh plugin --profile desktop install dsh-vm-control@1.1.1
# 或用本发行版附带的包
dsh plugin --profile desktop install ./dsh-vm-control-1.1.1.tgz
```

安装后**重启 DSH**。要求 Node ≥ 20，以及 VMware Workstation / Player / Fusion 提供的 `vmrun`。

## 升级说明 / Upgrade

- 从 1.1.0 升级无需迁移：`vms.json` 格式未变，插件数据目录原样沿用。

- 通过 VMware 界面暂停的虚拟机会显示为「运行中」——没有可查的命令行状态位。
- macOS / Linux 只采集 CPU 与 RSS，没有 IO 细分与线程数。
- 改写 VMX 只能在关机状态下进行（挂起状态允许，但会提示）。
- 只管理本机 VMware 产品；ESXi / vCenter 不在范围内。

# English

## Fixed

**`vm_power start` with `gui: true` could never return.** The root cause was not the timeout length: `runProcess` only listened for the child's `close` event, which fires once *all* stdio streams are shut. `vmrun start <vmx> gui` spawns `vmware.exe`, which inherits those pipes; killing `vmrun.exe` on timeout left the window holding them, so `close` never arrived and the promise never settled. The caller saw an unresponsive tool call rather than a timeout, the state-confirmation step never ran, and manual interruption recorded `TOOL_OUTCOME_UNKNOWN`.

`exit` now schedules a 250 ms fallback settle. The normal path still lets `close` win, so stdout stays complete; a pipe held by a grandchild is drained by the fallback. The grandchild is the VM itself, so it is never killed to close a pipe.

**Power waits share one budget.** The vmrun timeout and the following confirmation were timed separately (120 s start + 45 s confirm), so a stalled call could hang for 165 s. `timeoutMs` is now the total for the whole call and confirmation gets only what is left, with a 5 s minimum window because `vmrun list` often reflects the new state only a few hundred ms after the command returns.

**GUI starts default to 60 s.** A window appearing does not mean the VM is ready, and waiting longer only turns "started" into "timed out".

## Changed

- The "unconfirmed" result is phrased as "issued, not confirmed" with the facts that were established, keeping "no result was seen" apart from "the operation failed" and pointing at a state read instead of a resend (`vm.powerTimeout` → `vm.powerIssuedUnconfirmed` + `vm.powerFacts`).
- Tool descriptions say to prefer `gui=false`, that the timeout is a total for the call, and not to resend on an unconfirmed result.
- A confirmed headless start notes that it is faster than a GUI start and needs no desktop session.

## Measured

Cold start of a CentOS 7.9 desktop VM (8 vCPU / 4096 MB, VMware Workstation 17.6, vmrun 1.17.0) through the plugin's own `inventory.power()` path:

| Stage | nogui | gui |
| --- | --- | --- |
| `vmrun start` itself | 6.1 s | 2.9 s |
| `power()` returns (with confirmation) | 6.71 s · confirmed | 3.48 s · confirmed |

Also observed, unrelated to the tool but worth knowing: **`vmrun start` returning is not the VM being ready.** In that cold start `vmrun` returned after 3.1 s, while VMware Tools reported a guest IP only around 95–155 s later. To reach SSH, poll `getGuestIPAddress` or probe port 22; do not treat the `vmrun` return as the moment the guest is usable.

## Notes

- Upgrading from 1.1.0 needs no migration; `vms.json` and the data directory are unchanged.
- One behaviour difference: the GUI start timeout drops from 120 s to 60 s. Pass `timeoutMs` explicitly if your VM genuinely needs longer.
- Verified before packaging: 55 unit (including two new regressions) + 19 API + 5 client smoke + 5 integration + real cold-start runs on both nogui and gui through the full `power()` path.
